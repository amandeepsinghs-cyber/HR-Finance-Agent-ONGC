## 3. Page-reference accuracy
- **`source_page`** = number of `\f` before the text + 1 (SPEC-01 §4.1). Every non-`_flow` AR text has one form feed per PDF page. Text page counts match `pdfinfo` for all 8 PDFs (for example FY26 684/684).
- **Independent check against the PDFs** (scratch script `page_spotcheck.py`). For each sampled chunk it measures the share of the chunk's words (≥ 4 letters) found on the claimed PDF page and on the pages either side. Result: 40/40 have overlap ≥ 0.97 on the claimed page and are lower on both neighbours. ## 4. Retrieval hit@5 (`financial_ssot/knowledge/eval_ar_retrieval.py`)
The scoring rule is the same for both sets. The gold pages are the PDF pages of that AR where all of the question's regexes match, computed from the AR text. A question counts as a hit when a top-5 chunk has the same FY and a gold page (`--set main|heldout`; `--lexical-weight 0` gives vector + section only).

> [!WARNING]
> **The builder set (Q01–Q22) overstates retrieval quality. Use the held-out number (≈ 0.4) for decisions.**
> - **Lexical leakage:** I wrote the 22 questions with the gold regexes in view, so many reuse the answer page's rare terms (Daman Upside, Mumbai High, KG-DWN-98/2, Energy Strategy 2040, 51.11%).
> - **Topic skew:** 7 of 22 questions are about reserves/RRR (Q01–Q06, Q20), and Q06/Q20 share gold pages [7, 41].
> - **In-sample tuning:** `LEXICAL_WEIGHT` (D3) was chosen on this same set, so 0.77 → 0.82 is an in-sample gain of one question.

### 4.1 Held-out set (H01–H18): the number to use
- **What it contains:** H01–H08 are the G4 reviewer's paraphrases (P1.8.md §4.4). H09–H18 are new paraphrases written to avoid the gold page's distinctive vocabulary. Each reuses the gold regexes of the main question it paraphrases.
- **No tuning on it:** `LEXICAL_WEIGHT = 0.05` was frozen before this set was scored, and no parameter was changed afterwards.

| Run | hit@5 | Lenient (gold page ±1) |
|---|---|---|
| Hybrid (shipped default, LEXICAL_WEIGHT 0.05) | **7/18 = 0.39** | 9/18 |
| Vector + section only (LEXICAL_WEIGHT 0) | **8/18 = 0.44** | 10/18 |

Findings:
1. **Out-of-sample retrieval is weak (about 0.4).** Most misses land on the right topic but not the gold page:
   - H01 and H12 get the neighbouring p.99 or the AR FY25 version of the same paragraph.
   - H06 gets the CSR section p.194/195, which the narrow gold misses (G4 N3).
   - H13 (capex) and H17 (FY19 windfall) are clean misses.
2. **The lexical re-rank does not help out of sample** (−1 question). I recommend setting `LEXICAL_WEIGHT = 0` in P2F.5 unless a larger held-out set shows a gain. I did not change it here, because changing it after seeing held-out results would be tuning on the held-out set. Lead decision.
3. Improvements to try in P2F.5:
   - Use a 20+ question held-out set with hand-checked gold pages.
   - Embed the chunk heading together with the text.
   - Use a smaller `fiscal_year` window when the question names a year.

Per-question output: `financial_ssot/out/ar_retrieval_eval_heldout.json` and `…_heldout_vec.json` (gitignored).

## 6. Deviations and open questions
- **D1: the packet's ≥ 15,000 chunks could not be met under its own size rules. The target is now ≥ 8,000 per D-56 ✅.** The corpus is about 2.23 M whitespace words, or about 2.9 M estimated tokens. Chunks of at least 300 tokens with a 60-token overlap advance at most 240 tokens each, so the ceiling is about 12k chunks before the short/numeric drops. Pages under 300 tokens produce one chunk each. The chunker already uses the finest split allowed (every page with ≥ 462 words is cut into windows of about 300–360 tokens), which gives 8,712. Reaching 15k would need windows of about 200 tokens. The lead accepted ≥ 8,000 (D-56).
- **D2: query embedding is client-side.** The retriever uses `text-embedding-005` with `RETRIEVAL_QUERY` through the Vertex API, and passes the vector as an `ARRAY<FLOAT64>` parameter. SPEC-01 §8.2 names `ML.GENERATE_EMBEDDING`, which needs a BigQuery remote model and connection plus IAM. None of these exist, and creating them is out of scope.
- **D3: hybrid lexical re-rank added.** The re-rank adds a 0.05 × term-overlap bonus over 4 × top_k vector candidates.
  - On the builder set (in-sample) it took hit@5 from 0.77 to 0.82.
  - On the held-out set it lowers hit@5 from 0.44 to 0.39 (§4.1).
  - `LEXICAL_WEIGHT=0` gives vector + section ranking. Recommendation: 0 in P2F.5.
- **D4: files beyond Part B's three.** For Part A I added `financial_ssot/knowledge/{__init__.py, embed_load_ar.py, eval_ar_retrieval.py}`, `yukti/backend/app/knowledge/{__init__.py, ar_retriever.py}` and `yukti/backend/tests/test_ar_retriever.py`. `sections.yaml` is written as JSON-compatible YAML because the `financial_ssot` project does not depend on PyYAML, so `uv run` works without a lockfile change.
- **D5: known tagging weaknesses** (cosmetic; `heading` keeps the raw title):
  - ~~AR FY22 PDF p.18–57 tagged `ten_year`~~: fixed in chunker v2 (§8).
  - The statement pages just before the notes are sometimes tagged `notes`.
  - BRSR is a separate document from FY24 on, so brsr has 0–5 chunks in FY24–FY26.
  - `line_codes` holds keyword tags only (`KW.*`), because `financial_ssot/dim_financial_line.csv` does not exist yet. The chunker picks it up automatically when it exists. Until then the retriever skips non-`KW.*` line filters (C2, §8).
- **Not wired into the app yet.** No caller in `yukti/` uses `ar_retriever.py`; P2F.5 (SPEC-08 §6) does that.
