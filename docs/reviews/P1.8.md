## 1. Bottom line
- **The chunks, page references, verbatim text, BigQuery table and retriever SQL all pass independent checks.** Chunk count 8,712 meets the D-56 target (≥ 8k).
- **The headline retrieval number (hit@5 = 0.82) is inflated by lexical leakage in the self-authored question set.** When I reworded 8 questions to avoid the answer page's rare terms, hits fell from 7/8 to 4/8 (3/8 with pure vector). D-56 relies on "hit@5 met", so the evidence has to state this limitation honestly.
- **One latent defect in the retriever:** the `line_code` pre-filter silently returns `[]` for any real line code, because `line_codes` holds only `KW.*` tags until `dim_financial_line.csv` exists. It needs a guard before P2F.5 wires it up.

## 3. Non-blocking notes (follow-ups, not part of this verdict)
- **N1: index never populated.** `ix_doc_chunks_ar` is `ACTIVE`, `coverage_percentage = 0`, `last_refresh_time = NULL`. Also, the retriever always pre-filters on `fiscal_year`/`section`/`line_codes`, and these columns are not `STORING` columns of the index. So once the index is filled, VECTOR_SEARCH may still fall back to brute force, or post-filter and return fewer than `top_k` rows. At 8.7k rows brute force is fine. If the index matters, recreate it with `STORING(fiscal_year, section, line_codes)` (`embed_load_ar.py:177`). That is a DDL change and needs lead approval.
- **N2: FY22 PDF p.18–57 is tagged `ten_year`** (D5, confirmed: the FY22 `ten_year` range is p.18–301, 77 chunks). It affects the section re-rank: Q13's top-2 are FY22 p.48/p.28 tagged `ten_year`, which gets OTHER priority. Fix the carry-forward in `sections.yaml` (stop `ten_year` at the next major heading) in a later chunker version.
- **N3: gold strictness also hurts the score in the other direction.** For example, the paraphrased Q16 retrieved FY25 p.194/195 (the CSR section), but the gold regex `CSR expenditure of` accepts only p.103. Some gold sets are too narrow, so the eval is noisy both ways. Suggest a held-out set of 20 or more questions written without looking at the text, with hand-checked gold pages, in P2F.5.
- **N4:** `fy_window("FY00")` returns `FY99` (the modulo wraps). This is harmless.
- **N5:** a page-level hit gives credit to any chunk on the gold page, even when that window does not contain the answer sentence. This is lenient but acceptable.

### 4.5 Retriever SQL safety and FY pre-filter ✅
- All user-controlled values go in as query parameters: `@qvec` (ARRAY<FLOAT64>), `@top_k` (INT64), `@fys`, `@line_code`, `@sections` (`ar_retriever.py:161-171`).
- The only f-string interpolation is the table name, which is a module constant or a constructor argument (`:30, :74`). The question text never reaches the SQL. `maximum_bytes_billed` and job labels are set.
- `fy_window` validates `^FY\d{2}$` and raises otherwise. It returns `[fy, fy-1]` as SPEC-01 §8.2 requires, and the filter is applied inside the VECTOR_SEARCH base subquery, i.e. as a pre-filter (confirmed by the tests and by the eval top-5 lists, which show only fy/fy-1).
- The provenance label is `verified_ar` (SPEC-11). The module docstring correctly says that numbers must come from the structured views and not from chunk text.
- The loader is safe: it refuses an existing non-empty table, loads with `WRITE_EMPTY`, and uses `CREATE VECTOR INDEX IF NOT EXISTS`.
