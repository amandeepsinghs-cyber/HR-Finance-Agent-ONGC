    Gemini Live Is the Voice Front Door — Never the Calculator

    When you speak, Gemini Live (gemini-3.8-live) listens and picks one of two lanes: an instant Fast Lane for screen commands, or the Grounded Data Lane (ask_yukti) for every HR, Finance, policy, or valuation question.

    Two-Lane Voice Routing Architecture (yukti/backend/app/live_session.py) Voice: Leda (Indian English · Hindi · Hinglish)
    Tool 1 · Screen Control

    ui_control(action, value)

    Handles voice commands that change how the screen looks without running a new database query:

    • Charts: "Make it a waterfall / bar / table"
    • Overlays: "Overlay live Brent crude / rupee rate"
    • Exports: "Download as Excel / PDF / Word"
    • Theme & Filters: "Dark mode", "Only E5 and above"
    Tool 2 · All Data & Policies

    ask_yukti(query)

    Every question about numbers, people, policies, DCF valuation, or document drafting goes here:

    • Chart First: Pushes the visual card straight to the browser WebSocket so the chart appears immediately.
    • Voice Second: Returns a verified 2-sentence summary for Leda to read aloud in Lakh/Crore units.
    Voice Safety Rules

    Strict Guardrails on Speech

    System instructions + server code enforce three non-negotiable voice protections:

    • Zero Memory Answers: Forbidden from guessing any ONGC figure without calling ask_yukti.
    • Role Lock: Saying "Switch me to CMD" is refused; identity comes only from the signed cookie.
    • Clean Barge-In: Half-duplex echo gate prevents room speakers from re-triggering the mic.

    How Voice Turns Into a BigQuery Query — Without Any AI Writing SQL

    Yukti is fundamentally an aggregation (OLAP) problem: slicing headcounts, rolling up statements and applying corporate definitions across ~38 million rows. SQL is the native language for this, so AI plans the question and Yukti's code writes the SQL.     ❌ What Usually Breaks in Text-to-SQL Bots

    Letting an LLM write raw BigQuery SQL directly causes invented column names, wrong accounting subtotals, slow retry loops (~15s), and accidental leaks of restricted employee rows.

    ✅ How Yukti Solves It (v3/P5-one-brain)

    Gemini 2.5 Flash only picks what to measure (a JSON QuerySpec). Deterministic Python code (compiler.py) writes the exact SQL, enforces RBAC & a 500 MB cap, and checks every spoken digit.

    Your Question Changes Format 13 Times — Only 5 Steps Use AI

    Voice becomes audio, then text, then a dictionary of what is needed, then SQL, then numbers, then a chart and speech. AI only hears, understands and speaks; Yukti's code and BigQuery produce every number. Click a box to highlight who does it in the table below.

    Core design pattern · shared with Urvi (WellPulse)

    AI fills in a dictionary; trusted code does the filtering and computation

    Urvi uses narrow tools, so one AI step is enough. Yukti answers open-ended analytics across 86 tables, so a planner fills the dictionary.

    1 · Speech → dictionary AI

    Urvi: Gemini Live calls a narrow tool directly: well_profile({"well_id": "GK-129", "months": 36})

    Yukti: Gemini Live calls one broad tool, ask_yukti({"query": "…"}); Gemini 2.5 Flash then fills the plan: {"metric": "headcount", "dimensions": ["grade"], "filters": [...]}

    2 · Validate, call trusted code Code

    Urvi: well_profile(well_id, months)

    Yukti: QuerySpec.model_validate(plan) → access rules → compiler.compile(spec)

    3 · Filter and compute Code

    Filter by well, field, status, station, grade, tenure.

    Compute decline curves and ML classifiers (Urvi) or certified SQL on BigQuery (Yukti).

    4 · Verified output Screen + voice

    Screen: the full result (charts, tables, 3D map).

    Voice: a short summary spoken in English or Hindi; Yukti checks every spoken number against the result.

    What is the "dictionary"? (QuerySpec)

    Why a dictionary and then SQL? Yukti's questions are aggregations (headcounts, roll-ups, corporate definitions over millions of rows), and SQL is the native language for those. AI only fills in what is needed; certified SQL written by code applies ONGC's definitions the same way every time.

    Simply: Gemini Flash fills in a dictionary of what is needed, and the SQL builder turns that dictionary into a SQL command. Precisely, the form takes three shapes:

    1 · JSON text

    Gemini replies in a fixed answer format, so it can only return JSON in that shape.

    2 · Python dictionary

    The JSON is parsed into key-value pairs.

    3 · Checked form

    Every key and type is validated; a wrong field or a fiscal year like "FY2025" is rejected before any SQL is built.

    Example · "How many executives in Delhi for more than 5 years, by grade?"
    { "metric": "headcount", "dimensions": ["grade"], "filters": [ {"field": "wc", "op": "=", "value": "WC-DEL"}, {"field": "station_tenure_years", "op": ">", "value": 5} ], "grain": "aggregate" }

    It is more than flat key-value pairs: filters is a list of small forms, and period holds a year or a range. Follow-ups such as "only Mumbai" send a smaller patch that changes just those keys.
